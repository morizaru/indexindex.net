1. 指定実IPの ip_hash 照合後、access_logs で確認するSQL

SELECT
    ip_hash,
    is_bot,
    COUNT(*) AS pv,
    COUNT(DISTINCT visitor_hash) AS uu,
    COUNT(DISTINCT visitor_session_id) AS session_count,
    COUNT(DISTINCT path) AS path_count,
    COUNT(DISTINCT user_agent) AS ua_count,
    SUM(CASE WHEN referrer IS NULL OR referrer = '' THEN 1 ELSE 0 END) AS no_referrer_count,
    MIN(access_time) AS first_access,
    MAX(access_time) AS last_access
FROM access_logs
WHERE access_time >= '2026-08-19 00:00:00'
  AND access_time <  '2026-08-20 00:00:00'
  AND ip_hash IN (
      'computed_hash_1',
      'computed_hash_2',
      'computed_hash_3'
  )
GROUP BY ip_hash, is_bot
ORDER BY pv DESC;

実装した対策:

1. includes/access_logger.php

追加した bot UA 判定:
- HeadlessChrome
- python-requests
- curl/
- Go-http-client
- okhttp
- Scrapy

追加した bot 名分類:
- Headless Browser
- Python Requests
- curl
- Go HTTP Client
- okhttp
- Scrapy

追加した行動判定:
- Behavior Bot / Public Burst

判定条件:
- 対象 path は以下に限定
  - /indexindex/work.php
  - /indexindex/work_graph.php
  - /indexindex/ranking.php
  - /indexindex/search.php
  - /indexindex/works.php
- referrer が空
- 直近60分で同一pathの通常ログが80PV以上
- referrer 空が85%以上
- distinct ip_hash がPVの75%以上
- distinct visitor_hash がPVの75%以上
- distinct visitor_session_id がPVの75%以上
- distinct user_agent が8以下

目的:
既存の Behavior Bot / Distributed と Behavior Bot / Distributed Work の間を補完し、特定 work_id だけではなく通常公開ページ単位で分散・低UA・no-referrerの急増を拾う。

2. admin/access_analytics.php

追加・変更:
- Behavior Bot / Public Burst を bot 表示分類に追加
- 対策bot内訳、直近bot対策状況、botページ別アクセス数で Public Burst を表示
- 通常ログ側の Bot-like User-Agent 検出に HeadlessChrome / python-requests / curl / Go-http-client / okhttp / Scrapy を追加
- Normal Log Bot-like User-Agent / Behavior Candidates / Work ID Candidates / No-referrer Spike を選択期間 from/to ベースに変更
- Watched Real IP Hash Check カードを追加

Watched Real IP Hash Check:
- 画面で指定した期間内で、指定実IPから計算した ip_hash が access_logs に存在するか確認する
- salt は表示しない
- 表示するのはラベル、ip_hash先頭16文字、is_bot、PV、UU、session、path数、UA数、referrer空数、first/last

補正UPDATE案:
今回の環境では実データSELECTができなかったため、UPDATEは未実行。
実サーバーでSELECT結果を確認してから、対象を限定して実行する。
